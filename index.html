What ODF Suite is

ODF Suite is a set of three zero-dependency JavaScript libraries that parse OpenDocument Format (ODF) files in the browser. Each engine turns a ZIP container into a plain JSON AST, then renders it with the platform: semantic HTML and CSS Paged Media for printing, CommonMark for text, CSV and JSON for data. It is not a converter service and it does not need LibreOffice, WebAssembly or a backend.

03 / Why small

A parser, not an office suite

General-purpose office toolkits carry formats and machinery this task does not need. ODF Suite keeps the scope to three file types and hands the rest to the browser.

ODF Suite compared with a typical general-purpose office toolkit
 ODF SuiteTypical all-in-one office toolkit
FormatsODT, ODS and ODP, parsed nativelyOften DOCX / XLSX / PPTX first; ODF is an extra path
Runtime dependenciesNone. Every package has an empty dependency map.Usually ZIP, PDF, crypto or canvas helpers
Size17–23 KB minified per engineOne larger bundle for every format and feature
PDF outputBrowser print via CSS Paged MediaOften a bundled PDF or canvas pipeline
Data pathLocal parse; files never leave the pageVaries; conversion services are common
Trade-offODF only, read-only, no formula evaluationBroader formats and editing, with more weight

The comparison describes the common shape of all-in-one office libraries and hosted conversion tools, not a specific product. Pick the tool that matches the files you actually receive.

Platform over packages

DecompressionStream unzips. DOMParser reads XML. Blob URLs carry images. CSS Paged Media produces the print layout. Nothing is reimplemented in JavaScript that the browser already does well.

Structure, not a text dump

The AST keeps heading levels, inline styles, nested lists, cell spans, typed values, formulas, slide geometry and master backgrounds. Renderers read that AST; they never re-parse XML.

Local by default

Parsing happens on the device. That keeps confidential documents out of a conversion queue and makes the libraries work offline once the page is loaded.

Small blast radius

One package per format, no transitive installs, namespaced XML matching and tagged OdfError codes. The bundle stays auditable.

04 / How it works

Four steps, all in the page

  1. 01

    Unzip

    The ZIP central directory is read with DataView; each entry is inflated with native DecompressionStream('deflate-raw').

  2. 02

    Parse by local name

    Every lookup matches on localName, so office:, text: and table: prefixes can differ between producers.

  3. 03

    Resolve the cascade

    Default, named, automatic, parent and master styles become flat CSS declarations. Page layouts feed @page.

  4. 04

    Render or export

    Output semantic HTML, Markdown, plain text, CSV, JSON or a JSON AST. Call destroy() to revoke image Blob URLs.

Measured in Chrome, not assumed

ODT meets the 150 ms target for this 5 MB fixture; ODS and ODP are still above it, and a CPU profile shows why: decompressing the container takes 13–15 ms and the browser's own XML parser takes 62 ms (ODT), 112 ms (ODS) and 121 ms (ODP), so native parsing plus decompression alone is 125 ms and 134 ms of the 150 ms budget for the spreadsheet and presentation engines. Closing that needs a streaming parser instead of the browser's DOM. Under Node 20 with jsdom the same fixtures take roughly 0.95 s, 1.44 s and 1.46 s. The history records the methodology and the changes behind these numbers.

Repeated use stays flat: 40 parse, render and destroy() cycles on an 18 KB document with 120 images retain about 380 KB of heap in Chrome, and the image Blob URLs are revoked each time.

06 / FAQ

Questions, answered

Can I parse ODT, ODS or ODP files in the browser?

Yes. Each engine accepts a File, Blob, ArrayBuffer or Uint8Array and parses it locally with DOMParser, DecompressionStream and Blob URLs. The file never leaves the page.

Do I need LibreOffice, a backend or a conversion service?

No. The libraries read the OpenDocument ZIP and XML directly in JavaScript. There is no server-side conversion step and no native binary.

How large are the libraries?

The current minified bundles are 23.35 KB for odt-engine, 17.17 KB for ods-engine and 18.78 KB for odp-engine. Gzipped they are 8.97 KB, 7.05 KB and 7.69 KB. Every package has an empty runtime dependency map.

Can I convert an OpenDocument file to PDF?

Yes. toHTML() returns a complete HTML document with CSS Paged Media rules. Pass it to triggerPrintToPDF or load it in an iframe and call print(); the browser produces the PDF.

Do the libraries support DOCX, XLSX or PPTX?

No. They are deliberately OpenDocument-only. Legacy binary formats and Microsoft Office XML formats are out of scope.

Are spreadsheet formulas evaluated?

No. Formulas are preserved verbatim in the AST and in exported values. The engines read cached cell results rather than recalculating the workbook.

What are the known limitations?

The engines are read-only. ZIP64 archives are rejected, encrypted entries are skipped, ODT footnotes and comments are not in the AST, and slide animation and media are not rendered. They are built for documents in the low-megabyte range.

Can I use the libraries without npm or a build step?

Yes. Each engine is a standalone ES module. Import it straight from jsDelivr or GitHub Pages, or unpack one engine folder into your project with a single curl command. Nothing is installed and nothing is built.
